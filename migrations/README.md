# Database schema

These files are the schema of record. They used to live in `backend/`, the
Express application — the schema outlived it, so it moved out before that
folder was deleted.

## Layout

| | |
|---|---|
| `NNNN_description.sql` | The migrations, applied in numeric order. Never edit one that has run. |
| `schema.sql` | A `pg_dump --schema-only` of the current state. Reference only — nothing applies it. Regenerate after adding a migration. |

## Applying them

`tools/migrate.py` runs the pending ones and records them in a
`schema_migrations` table, so "is this database up to date?" has an answer that
is not someone's recollection. Before it existed, 0007 and 0008 were applied to
production by piping the file over SSH and remembering.

```bash
python tools/migrate.py --url "$DATABASE_URL" --status
python tools/migrate.py --url "$DATABASE_URL" --apply
```

Every migration runs in its own transaction and is recorded in that same
transaction, so a failure leaves neither a half-applied file nor a false record.

Both the local database and production were baselined on 2026-08-21: all ten
files are recorded as applied without having been re-run, because they already
were. A database created from scratch instead needs `--apply` from empty.

## Adding one

Write `NNNN_what_it_does.sql` with the next number, run `--apply` locally, then
regenerate `schema.sql`. Against production, take a backup first — see
`Desktop/oracle/backup_db_beyblade/` for the convention — and expect `--status`
to report a checksum mismatch if you edited a file after it ran, which is the
tool telling you the database and the repo have diverged.

## Where the shape comes from

Historically these were generated by Drizzle from `backend/src/shared/schema.ts`.
The FastAPI backend does not use an ORM — it issues SQL directly — so with
Express gone there is no generator, and these files are the definition rather
than its output. The Drizzle schema is in the git history up to `465343b` if
you ever want the typed description back.
